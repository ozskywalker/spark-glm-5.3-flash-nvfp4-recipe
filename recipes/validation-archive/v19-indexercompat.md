## Ninth incident: a real production crash, back on `v15-combined`, no NVRM/Xid signature at all

Roughly an hour after the downtime window closed and production traffic resumed, `v15-combined` crashed under real traffic: `EngineDeadError`, no Python traceback anywhere upstream of the cascading shutdown, no kernel-level Xid or `NV_ERR_NO_MEMORY` entry in `journalctl -k` for the full window (checked both the ten minutes immediately before the crash and the wider window back to the preceding JIT-compile event). Node1's uptime (unchanged since this morning's earlier reboot) and node2's (4+ days, unbroken) both confirm **no host reboot** -- this is squarely the older, still-unexplained "silent kill" signature this project has never fully attributed (the same class as the Sep 3 "third crash, OPEN" and Sep 6 "0.85 crashed" incidents), not a recurrence of today's fragmentation/Xid-31 mechanism.

A Triton JIT compile (`BuildPrefillChunkMetadataKernel.kernel` -- the same kernel implicated in this morning's fresh-boot crash) fired ~10 minutes before the crash began. That gap is much longer than the ~2-20 second compile-to-crash windows seen in every prior compile-adjacent incident (crash-4, this morning's fresh-boot crash) -- a real, useful negative data point against "the compile itself is the trigger": either this is coincidental timing, or the actual mechanism has more lead time than previously assumed. Not resolved.

Cleaned up a zombie `Worker_TP1` process left holding ~101 GiB of GPU memory on node2 (same pattern as every prior crash-with-lingering-worker this project has seen), flushed with the new fragmentation pre-flight check -- both nodes reported tens of millions of contiguous free blocks, ruling out fragmentation as a factor in this specific crash -- and rebooted clean. Production restored, sanity-confirmed (`HTTP 200`, coherent completion).

**Correction, found ~35 minutes later when the same thing happened again and got a proper investigation**: the "no known cause" attribution above was wrong -- it was based on `journalctl -k` (kernel log) alone, which was the wrong log to check. `journalctl -u earlyoom` tells the real story:

```
Sep 08 20:26:18 spark-2dd4 earlyoom[1600]: low memory! at or below SIGTERM limits: mem  2.00%, swap 80.00%
Sep 08 20:26:18 spark-2dd4 earlyoom[1600]: sending SIGTERM to process 844563 uid 1000 "python3": badness 984, VmRSS 3344 MiB
```

**`earlyoom` killed the process, deliberately, exactly as configured.** The API server's own log confirms the causal order once you know to look for it: `[shutdown] API server: shutdown triggered` fires *first*, then the API server itself sends SIGTERM to EngineCore as part of its own teardown -- the `EngineDeadError` seen downstream is a *symptom* of that shutdown cascade, not evidence of an internal crash. Every "no traceback, no Xid" observation in this entry (and, in hindsight, plausibly some earlier ones in this document) is exactly what an external SIGTERM looks like from inside the process being killed: there's nothing to traceback, because nothing went wrong inside the code.

A second, identical earlyoom kill fired 34 minutes later (`21:00:41`, `badness 989, VmRSS 4506 MiB`) during the restore that followed -- and checking node1's *full day* of `earlyoom` history turned up two more, both predating tonight and previously undocumented: `12:38:39` and `14:35:41`. **Four real earlyoom kills on node1 today, zero on node2.** This is not a mysterious signature; it's this project's own already-documented `gpu_memory_utilization`/earlyoom margin issue (the 0.86 regression, the 0.85 crash, the 240K margin work earlier in this document), just tripping under ordinary traffic tonight instead of requiring a deliberate stress test to reach.

**Leading explanation for why node1 specifically, and why today specifically**: node1 is the head node -- it runs the API server, tokenizer, and request/response handling in addition to being a TP worker, while node2 runs a leaner worker-only process. That structural asymmetry means node1 has less headroom at the same `gpu_memory_utilization` to begin with, and today involved an unusually high number of boot/reboot cycles (10+, across the fragmentation investigation, the dense-FP8 build/validate/reject cycle, and the restores that followed each crash) -- this project has already observed once before that repeated rapid reboots erode the safe margin further than its resting baseline ("v9 promoted" earlier in this document: 0.84's own safe margin shrank from ~5.5% idle to ~2.9% under load across a single long session of testing). Not yet proven which factor dominates; both point the same direction.

**Practical upshot**: the Triton-compile correlation noted above (and in this morning's fresh-boot incident) was very likely a coincidence, not a lead -- `earlyoom`'s own log is the correct place to check first for this exact "no traceback, clean shutdown cascade" signature, before spending time on kernel logs or JIT-compile timing. Worth adding an `earlyoom`-log check to this project's standard crash-triage checklist alongside the existing `journalctl -k` / fragmentation checks. Production restored a third time, confirmed healthy; node1's margin measured ~5.6% immediately post-boot (7,025 MiB / 124,610 MiB) -- comfortably clear for now, but per this project's own repeated finding, idle/just-booted margins have not reliably predicted margins under real load.

## Upstream sweep 2026-09-09: a real, currently-live quality bug in our own chat template

Routine re-check of all five tracked upstream repos (MiaAI-Lab, Enntity/sparkglm, mmastrac/mentat, mmastrac/glm-5.3-flash-4x-gx10, tonyd2wild/DFlash2). Two found no new commits since their last review (`glm-5.3-flash-4x-gx10` still at `a30d4b24`, DFlash2 fork still at `050081dc`) -- nothing to act on there. The other three had real movement; one item is a live production bug.

**MiaAI-Lab, PR #150 (`a5cc0048`, merged 2026-09-09): the Reasoning Effort head line was leaking reasoning into the answer channel on every thinking-disabled request, on both their fleet and ours.** Their `chat_template.jinja` (and ours, grafted from the same upstream base) emitted `<|system|>Reasoning Effort: Max` unconditionally, even with `enable_thinking=False`, on the theory that keeping the head line stable protected the prefix cache across a thinking toggle. Upstream's own before/after measurement: with the line present and thinking off, spark-bench code dropped 98 -> 60, structured 97 -> 58, with syntax errors and malformed fenced JSON at temperature 0.3. The fix gates the line on `thinking_enabled`; the accepted cost is that toggling thinking now re-prefills the prompt (upstream's own call: correctness over cache stability, since agent traffic doesn't toggle mid-conversation anyway).

**This was not a hypothetical for us.** `glm-5.3-flash-exl3-v15-combined-vllm.yaml:705` sets `default_chat_template_kwargs: '{"enable_thinking": false}'` -- thinking is **off by default** on our production traffic, meaning this bug was live on effectively every request our fleet has served since this template line was first introduced, not just an edge case. Our own `tests/test_chat_template.py` had explicitly encoded the old, buggy assumption as intended behavior (`test_thinking_can_be_disabled` asserted the head line *should* stay present) -- the same tradeoff upstream made and later reversed after actually measuring the damage.

**Fixed in the build tree** (`recipes/build/glm53-exl3-v15-combined/files/chat_template.jinja`, one-line change: gate the head-line `{%- if -%}` on `thinking_enabled`) and the test suite updated to match upstream's corrected assertions (`recipes/build/glm53-exl3-v15-combined/tests/test_chat_template.py`, ported verbatim from `a5cc0048`). All 7 tests pass locally. **Not yet built into an image or booted** -- this is a template-only change, but changing it still requires a container restart to take effect on running production, so it needs the same scheduled-downtime treatment as any other production change, even though the diff itself carries none of the risk a kernel/build change would.

Two smaller upstream items checked and found not actionable right now:
- MiaAI-Lab #146 (`d7dd7de9`): raised `LIMIT_MM` image cap 4 -> 100 (validation ceiling only, nothing reserved for it). We run vision on with `limit_mm: '{"image":4,"video":1}'` (`v15-combined-vllm.yaml:704`) -- fine to leave as-is unless a real workload needs more than 4 images per prompt.
- MiaAI-Lab's own `.env.example`/README update recommending a 14 GiB (not 15 GiB) KV cap when combining `GLM53_DENSE_FP8` with `GLM53_ADAPTIVE_K` under DFlash2 k=7 -- not applicable to us: we already rejected dense-FP8 on our own numbers (see above), and adaptive-k has no analog under this fleet's MTP-2 config (see the MiaAI-Lab update analysis entry, earlier in this document).

**Enntity/sparkglm has moved its `main` branch default off EXL3 entirely**, to a measured NVFP4 path (native CUTLASS W4A4, MXFP8 DFlash2, 512K context) -- explicitly flagged by the maintainer as "a source research preview... not a production certification." The EXL3 grouped-prefill kernel work we actually run in production (ported from this repo, `EXL3_GROUPED_PREFILL_K4`) is preserved on the `exl3` branch, not `main`. Practical implication: future monitoring of this repo for EXL3-relevant changes should watch the `exl3` branch specifically, since `main`'s activity is now NVFP4-focused and largely irrelevant to our stack.

**Worth a dedicated look later, not done here**: sparkglm's own `docs/KNOWN_LIMITATIONS.md` documents a "model-semantic approximation in sparse MLA" -- GLM-5.3's indexer can emit up to 2051 candidates, but the FlashInfer SM121 sparse-MLA kernel is fixed at exactly 2048, so their compatibility overlay silently drops up to 4 of the lowest-ranked pooled candidates per affected row. We run the same base image, same exllamav3 commit, and the same FlashInfer SM121 sparse-MLA path (`FLASHINFER_CUDA_ARCH_LIST=12.1a`, `--no-enable-flashinfer-autotune`) -- this is very likely present in our own production serving too, and has never been checked or documented in this project before now. Small magnitude (at most 4/2051 candidates on affected rows) but a real, previously-unflagged model-semantic deviation baked into the shared upstream kernel, not something we introduced. Flagging for a future investigation, not chasing tonight.

**mmastrac/mentat** shipped 0.7.0 and 0.8.0 (`cbd6b41c`, `1350b489`), including a real reliability fix: a daemon that isn't the head now relays every agent registration to whichever daemon actually holds the head, fixing a "waiting for N GPUs, have 1" hang when a container's `RAY_ADDRESS` pointed at itself instead of the real head. This is the exact troubleshooting item documented in `mmastrac/glm-5.3-flash-4x-gx10`'s README. Not actionable for us -- Track 3 (Mentat pilot) remains closed, since our deployment uses vLLM's `mp` executor, not `ray`, so there's no Ray control-plane surface for Mentat to attach to. Noted only as evidence Mentat continues to mature, in case that track is ever reopened.

## Follow-up investigation 2026-09-09 (production quiet, no downtime used): sparse-MLA truncation closed out, two retroactive/live findings on other open threads

Three separate investigations, run back-to-back while production traffic was light. No boots, no restarts -- read-only log/source inspection plus one docker-exec into the live production container.

### 1. Sparse-MLA candidate truncation (from the upstream sweep above): already correctly handled, nothing to fix

Read `recipes/build/glm53-exl3-v15-combined/Dockerfile`'s own header comment (lines 1-97) in full -- this project had already independently documented the exact 2048-vs-2051 problem sparkglm's `KNOWN_LIMITATIONS.md` flags, in far more technical depth (FlashInfer's SM120 sparse-MLA kernel instantiates `topk` only at `{128,512,1024,2048}`; GLM-5.3's kpool indexer can emit up to 2051: 512 pools x `index_kpool=4` + up to 3 always-selected recent-tail tokens). **The mitigation is already implemented**, not just documented: `sparse_attn_indexer_kpool.py`'s `expand_pools_and_append_tail` calls are patched (Dockerfile lines 269-290) to slice `pool_ids[:, :select_k - 1]` before expansion -- dropping the single lowest-ranked pool (511 of 512, 2044 tokens) rather than truncating the tail, since the recent tail carries the highest attention weight in a causal model and can never be recovered from the compressed pools. This is the same strategy sparkglm converged on independently ("expands 511 pools and preserves the recent tail"). Checked FlashInfer upstream (`flashinfer-ai/flashinfer`) for any kernel change that would accept the full 2051 width natively -- nothing found; the only relevant merged PR (#3395) is the one that introduced the SM120 sparse-MLA kernels with this exact limitation, back in June. **No action needed** -- this was a false alarm in the sense that it looked like an open gap from the outside, but is in fact already the best-known mitigation, already shipped.

### 2. Retroactive earlyoom check on the Sep 3 and Sep 4 "unexplained" crashes: one confirmed match, one confirmed ruled out

Per [[earlyoom_root_cause_correction]]'s own flag that older incidents were never checked against `journalctl -u earlyoom`, went back and checked both.

**The 2026-09-04 `gpu_memory_utilization=0.85` crash (recorded at 03:40:23 UTC) is definitively NOT earlyoom.** Node1 runs `America/New_York` local time (EDT, UTC-4 in September), so 03:40:23 UTC is 23:40:23 local -- pulled `journalctl -u earlyoom` for that exact window: memory available was flat and stable at 4.03% (5,022-5,026 MiB), nowhere near the 2% SIGTERM threshold, no kill event within 8 minutes in either direction (the nearest kill that night was at 23:48:44 local, sending SIGTERM to a `VLLM::Worker_TP` process -- 8 minutes *after* the recorded crash, too late to be the cause, and at a healthy 3.4%+ margin when it fired). This crash remains a genuine, distinct, unattributed "silent kill" -- the earlyoom explanation does not generalize to it, which sharpens rather than dissolves that mystery.

**2026-09-03 (the day of three separate production crashes, the third left as "matches an unresolved open upstream issue, not confirmed") had six real earlyoom kills on node1, zero on node2**: 01:02:26, 12:22:21, 14:34:41, 16:40:39, 17:14:17, 23:48:44 (all local/EDT), targeting a mix of `VLLM::Worker_TP` and `python3` processes. This is the same head-node-only asymmetry [[earlyoom_root_cause_correction]] found on 2026-09-08 -- six days earlier than first identified, and at similar volume (six kills in a day, vs. four on the 8th). VALIDATION.md's original write-up of that day's crashes doesn't record exact wall-clock times for the three incidents, so an exact 1:1 timestamp match to a specific documented crash isn't possible after the fact -- but the symptom pattern lines up well: several of these kills targeted `VLLM::Worker_TP` directly rather than the API server process, and a worker dying on one node while the API server survives is exactly the "node0 lost its entire process tree, node1 left an orphaned `Worker_TP1`" shape recorded for that day's crashes. **Not claiming a confirmed match for lack of exact timestamps, but this meaningfully raises the odds that the "third crash, unconfirmed" entry from Sep 3 was also earlyoom, not the `#54317`-pattern lead it was filed under** -- and confirms the head-node asymmetry is a standing, multi-day pattern, not a one-off from an unusually busy Sep 8.

### 3. The recurring NCCL/shared-memory-broadcast boot stall (7th+ occurrence across this project's history): a strong, unconfirmed lead, worth a dedicated session

This project has hit `shm_broadcast.py`'s "No available shared memory broadcast block found in 60 seconds" during real-checkpoint boots repeatedly (v12-combined promotion, v15-combined promotion, v16-densefp8 validation -- always at the same 14th-of-15 CUDA-graph-capture-size point, i.e. capture size 24 in this fleet's `1 2 3 4 5 6 8 9 10 12 15 16 20 24 32` list). The leading theory carried into this session (sparkglm's own comment about ephemeral Triton/TileLang JIT caches causing a 600s NCCL watchdog stall) is **already fixed in our build** -- both `TRITON_CACHE_DIR` and `TILELANG_CACHE_DIR` are host-persisted (`start.sh:298-307`, `v15-combined-vllm.yaml:609`) -- yet the stall still recurs, meaning that fix was necessary but not sufficient, or addresses a different trigger than the one actually firing here.

Searched `vllm-project/vllm`'s issue tracker for the exact log message and found a strong architectural match: **issue #51921**, same hardware family (4x GB10/SM121a, aarch64, `mp` executor), diagnosed down to "the head's EngineCore is blocked *reading* (the `acquire_read` warning, not `acquire_write`) -- the thing that should be writing has stopped," which the issue's own commenters traced to **PR #51538** / issue #51593: a **negative context-length underflow in padded MTP decode slots**. When a decode batch includes a zero-length padding row (e.g. during CUDA-graph-capture warmup, which synthesizes dummy requests to fill out each capture-size shape) and `next_n > 1` (our `MTP_TOKENS=2` config), the per-token length computation `seq_len - max_decode_len + local_idx + 1` goes negative for the first token of that padded row. Read as `uint32` downstream, `-1` becomes `~4.29e9`, which a cooperative-launch top-k kernel can read as a real row length far past its buffer, walking into undefined behavior -- or in the case this project has repeatedly hit, apparently deadlocking a worker mid-kernel, which starves the shm_broadcast ring buffer the head is reading from and produces exactly this project's own repeated symptom (a permanent per-60s warning, recoverable only by a full restart).

**Confirmed via `docker exec` into the live production container** (`sparkrun_79c5edfe845e0a06_5ce1214c28bf_node_0`, read-only, no restart) that the exact vulnerable, unpatched pattern from before PR #51538 is present verbatim in our image's `vllm/v1/attention/backends/mla/indexer.py` (`per_token_seq_len = seq_len - max_decode_len + local_idx + 1`, no `tl.maximum(..., 0)` clamp; `seq_lens_buffer[:] = (...)`, no `.clamp_(min=0)`). **However, this is not a confirmed root cause for our specific stall**, for one real reason found while checking: GLM-5.3's actual decode path for kpool indexing (`sparse_attn_indexer_kpool.py`, since this checkpoint uses `index_kpool=4`) computes its `seq_lens` independently of `indexer.py`'s vulnerable function, and (because of this project's own existing `_disable_gb10_persistent_topk` patch, which routes GB10 away from `persistent_topk` and onto `torch.ops._C.top_k_per_row_decode` for exactly the smem-oversubscription reason documented in `patch_glm_video_placeholders.py`) our actual fallback kernel is `top_k_per_row_decode`, whose CUDA source is not shipped in the runtime image to inspect directly -- so it's unconfirmed whether that specific kernel shares the same unclamped-negative-length vulnerability the upstream fix patched in `cooperative_topk.cuh`/`persistent_topk.cuh` (kernels we don't call, having already routed around them for a different reason).

**Verdict: a strong, well-evidenced, but not confirmed lead.** Same hardware family, same MTP+sparse-MLA combination, same symptom text, same "reader blocked, writer never showed up" diagnostic signature, and the vulnerable *pattern* confirmed present in-image -- but the specific kernel our GB10 fallback path actually calls wasn't touched by the upstream fix, and its internals aren't inspectable from what's shipped in the image. **Not applied this session** -- porting the Python-side clamp (`indexer.py`, two small changes, zero downside even if it turns out not to be on our hot path) is cheap and worth doing on principle, but confirming this actually closes the recurring stall needs a dedicated boot-and-reproduce cycle (the stall is intermittent, not every boot, so a clean pass after patching wouldn't be conclusive without several repeat boots) -- a good candidate for the next scheduled downtime window that isn't otherwise full.

## Promoted: glm-5.3-flash-exl3-v19-indexercompat-vllm.yaml is now the shipped default (2026-09-10)

vLLM v0.29.0's release notes were triaged for backport candidates against this fleet (4 real candidates identified: #54048, #53785-vs-our-own-#55738, #51718, and three SM120 sparse-MLA fixes). #54465 (BLHNC cache addressing) was ruled out by read-only `docker exec` inspection of the then-live production container plus the actual PR diff -- both halves of that fix touch code paths GLM-5.3-Flash on GB10 never executes (DeepSeek-V3.2-only Triton kernel; a DCP-gated branch we don't use at `dcp_world_size=1`) -- no boot needed. The three SM120 sparse-MLA/decode-topk fixes (#51395, #53574, plus #54465 above) were confirmed either already independently fixed in our own fork or not exercised by our code paths.

The remaining three candidates went through a real build-and-validate round, sequentially, in one downtime window (production stopped 2026-09-09 ~23:23, tinyGLM-gated before every real-checkpoint spend, matching this project's standing discipline):

1. **#55738 (dense/masked-MHA for GLM-5.3-Flash's NoPE (256,0,256) layout) -- built (`v17-nopemha`), tinyGLM-tested, NOT promoted.** Correctly scoped down to commit 3/3 only (commits 1/2's masked-MHA allow-list re-confirmed inapplicable to our tree, same reason found in the original v10-vllmpatch/v12-combined research: `flash_attn.py` fails to import, `_is_masked_mha_available` is SM100-gated). The scoped-down patch is **structurally dead code**: `FlashInferMLASparseSM120Impl` -- the class GLM-5.3-Flash actually instantiates on GB10 -- hardcodes `supports_dense_mha_prefill = False`, which is this fork's *own* independent fix for upstream #51395 (already shipped, unrelated to this session). That flag forecloses the entire dense-MHA-prefill code path before any of #55738's logic can run. Confirmed empirically: tinyGLM booted clean, but the patch's own diagnostic never fired across 3 request sizes spanning fresh-prompt through chunked-prefill regimes, and the boot log carries the plain-language confirmation: `Sparse MLA impl has no dense-MHA prefill path; using the top-k MQA path only.` Real-checkpoint boot skipped as unnecessary (the attribute is static on the backend class, not checkpoint-dependent).
2. **#54048 (cuBLAS out_dtype router GEMM, explicitly named upstream as fixing "family-120/GB10") -- built (`v18-gb10gemm`), PASSED, promoted.** Distinct from our already-shipped `patch_moe_gate_dedup.py` (that's a duplicate-*call* dedup in `model.py`; this fixes which GEMM *tier* the surviving call gets in `gate_linear.py` -- the fused fp32-accumulating cuBLAS epilogue vs. a bf16-rounding fallback). Zero anchor reconciliation needed -- our installed `gate_linear.py` matched the upstream diff byte-for-byte. tinyGLM: clean, new diagnostic fired confirming the widened path engages on GB10. Real-checkpoint: `probe_sanity.py` ALL PASSED, decode 27.95-29.59 tok/s (at/above the pre-round baseline of 26.9-28.5); `probe_longctx.py`@16K ALL PASSED, TTFT 10.7s (baseline ~9.9s, within noise for a precision fix). One earlyoom kill hit mid-run (`journalctl -u earlyoom` confirmed the standard mem 2.00%/swap 80.00% trigger) -- not attributable to this patch (`gpu_memory_utilization` unchanged, no new/larger buffers added), read as this fleet's already-documented thin memory margin recurring under load; recovered clean with `prelaunch_flush.sh` + retry.
3. **#51718 (KV-cache layout refactor, upstream rename of `compress_ratio`->`tokens_per_state` and `storage_block_size`->`num_states` in `indexer.py`) -- hardened `patch_indexer_workspace.py` (`v19-indexercompat`, built on `v18-gb10gemm`), PASSED, promoted.** This isn't new functionality -- our current base predates the rename entirely -- so the change is defensive: the patch's anchor-matching now tries the current attribute names first and falls back to the post-#51718 names, raising its existing fail-closed error only if neither matches. Confirmed behavior-neutral on our current base (identical `[glm53-indexer-workspace] builder: compress_ratio=4 workspace=1048592 entries` diagnostic line as every prior build). Unit tests extended to cover both anchor shapes.

**A real incident during item 3's real-checkpoint validation, disclosed plainly**: the first boot attempt hit this fleet's recurring NCCL/shm-broadcast stall (see the section above this one) and, unlike the three prior occurrences in this project's history (each resolved after one retry within minutes), **did not self-resolve** -- it repeated for the entire ~6.2 hours the job was left up (371 log-line repeats, ~1/minute), while the subagent driving that boot went silent instead of retrying or escalating. This left **production down roughly 6.5 hours total**, well past the intended validation window, before it was caught by the user asking for a status check. Recovered with the standard remedy (stop, `prelaunch_flush.sh --during-load` on both hosts, retry) -- second attempt booted clean with zero stall recurrence, and full validation passed (`probe_sanity.py` decode 27.4-29.85 tok/s across two separate runs, `probe_longctx.py`@16K TTFT 9.7s / 4-4 codes retrieved, determinism confirmed via byte-identical temp=0 output). **Operational lesson for this project going forward**: a subagent driving a real GPU boot during a downtime window needs either a hard time-box with an explicit escalation trigger, or direct supervision through the boot reaching a terminal state -- passively waiting on a notification is not sufficient, since the thing being waited on can hang indefinitely with production down and nothing else watching.

**Verdict: promote.** #54048 and the #51718 hardening both verified clean with no measured regression; #55738 correctly excluded (confirmed dead code, not a loss). `recipes/glm-5.3-flash-exl3-v19-indexercompat-vllm.yaml` is now the shipped default. `v18-gb10gemm`, `v15-combined`, `v12-combined`, and `v9-fatfork` all retained as known-good rollback targets, in that order of preference.
