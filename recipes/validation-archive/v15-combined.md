### Item 1: the 240K memory-pressure risk, confirmed and correctly characterized as beyond this diagnostic's reach

Booted `glm-5.3-flash-exl3-v13-oomtrace-vllm.yaml` (v13-moegemm base, OOM-observer armed via `TORCH_MEM_TRACE_DIR`/`TORCH_MEM_STATS_DIR`, `TORCH_MEM_FRACTION` deliberately left unset). Sanity passed clean. Deliberately reproduced the exact 240K-token single-request scenario that triggered NVRM OOM events during the v12-combined promotion. **The same `NVRM: nvCheckOkFailedNoLog: Check failed: Out of memory [NV_ERR_NO_MEMORY]` events fired again, on both nodes** -- the 5th reproduction across every kernel/patch combination tested this project (E3-on, E3-off control, and now the moegemm-patched build too). Node 2's margin dropped to 2.14% mem-available, the closest to earlyoom's 2% trigger observed yet.

**The OOM-observer's trace directory was empty on both nodes afterward -- no snapshot was written.** Checked the per-worker allocator stats file, captured at the moment of the failure window: `allocated=101.6 GiB, reserved=104.4 GiB (== max_reserved, i.e. plateaued), device_free=5.8 GiB` out of a 130.66 GiB CUDA device_total. **PyTorch's own allocator had 5.8 GiB of headroom in its own pool at the exact moment the kernel-level NVRM allocation failed.** This means the failure is not a normal `cudaMalloc`-style out-of-memory event that PyTorch's `torch._C._cuda_attach_out_of_memory_observer` hook is designed to catch -- it's happening at a lower level (the NVRM driver's own `_memdescAllocInternal`, most likely a host-side page allocation backing a GPU memory descriptor on this unified-memory platform, under host-level memory pressure). This exactly matches the caveat flagged before attempting this test ("if the 240K failure is a lower-level NVRM/driver hard error rather than a clean PyTorch allocator-level OOM, this observer might not fire at all") -- confirmed, not just theorized.

**Conclusion: this is a genuine, reproducible, driver/host-level memory-pressure condition, independent of kernel choice and independent of the MoE gate-dedup patch, that the OOM-observer diagnostic (as built) cannot directly instrument.** A real trace of this specific failure would need either a host-level tool (e.g. tracing the NVRM/nvidia-smi driver calls directly, or `/proc/meminfo` sampled at very high frequency right around the failure) or catching it via a kernel-level mechanism, not a PyTorch-level one. Given the margin was already at 2.14% (uncomfortably close to a real kill) at the moment this was confirmed, further escalation (e.g. testing single-vs-concurrent-request sensitivity at this same scale) was deliberately not attempted this session -- flagged for a future, more cautiously-paced investigation, ideally with host-level tracing tooling prepared in advance rather than a PyTorch-side observer.

## Host/driver-level trace of the 240K failure: fragmentation confirmed as root mechanism, plus a new, higher-severity escalation path found

Direct continuation of the "still open" item above -- user asked for a host/driver-level trace of the 240K failure (not another PyTorch-side observer), plus FlashKDA numbers at 128K/240K. Built `mem_trace.sh`, a 100ms-interval sampler of `/proc/meminfo` + per-zone `/proc/zoneinfo` watermarks/free-page-blocks + `/proc/vmstat` reclaim/compaction counters, run in parallel with live `journalctl -k -f` followers on both nodes (plain `dmesg -T` was intermittently unreliable on this fleet even under `sudo -n`; `journalctl -k` was consistent).

### The discriminator: contiguous free-block count, not raw free memory

Ran the 240K scenario against the already-running, ~40-minute-idle-since-its-own-graph-capture v15-combined production boot ("settled boot"): **succeeded cleanly**, zero NVRM events, zero change in `compact_stall`/`compact_fail` counters, margin stayed flat. Then did a fresh `prelaunch_flush.sh` + reboot of the identical recipe and ran the same 240K request within ~2 minutes of boot completion ("fresh boot"): **crashed** with `EngineDeadError` (no NVRM entry this time -- a genuinely different signature, matching the historical "silent kill" pattern with zero traceback). A live Triton JIT compile (`BuildPrefillChunkMetadataKernel.kernel`) fired ~2s before death, but grepping the successful run's own log confirmed the *same* compile event fired harmlessly there too -- ruling out "the compile alone causes it."

Comparing node 2's traced `/proc/zoneinfo` at the analogous moment in each run: `Node 0, zone Normal: nr_free_pages_blocks` was **147,456** during the successful settled-boot run's compile event vs. **0** during the failed fresh-boot run's compile event. Raw `MemAvailable` looked broadly similar in both cases (~2.1-4.5% margin) -- the number that actually discriminated success from failure was contiguous higher-order block availability, not the percentage-based margin this project has been checking all along. This explains why idle-margin checks have repeatedly looked "safe" right up until a real failure: a node can show acceptable raw free memory while having zero usable contiguous blocks for whatever large/higher-order allocation NVRM's `_memdescAllocInternal` needs. Practical read: a boot that's been idle long enough for the kernel to consolidate memory back into large blocks tolerates a 240K prefill; a fresh boot's own weight-load/graph-capture churn leaves memory freshly fragmented and measurably more exposed. This is a single data point per condition, not yet statistically robust, but it is a real, mechanistically coherent answer to the trace the user asked for.

### New, higher-severity finding: a GPU MMU fault (Xid 31) can escalate to a full host reboot on this platform

While restoring production after the fresh-boot test, two consecutive boot attempts failed with genuinely different, non-silent errors on node 1 (`spark-2dd4`): an `NCCL error: unhandled cuda error` during the CUDA-graph warmup allgather, then (on the very next attempt, after confirming and clearing a zombie `Worker_TP1` process left holding ~97 GiB of GPU memory from the first failure) a `torch.AcceleratorError: CUDA error: an illegal memory access was encountered`. Node 1's kernel log for the prior boot showed the real chronology: **9 separate `NVRM: nvCheckOkFailedNoLog: ... NV_ERR_NO_MEMORY ... _memdescAllocInternal` events between 10:55 and 12:55** (the same signature chased all session), then **two Xid 31 GPU MMU faults** nine minutes apart (12:56:15, 13:05:45), both `FAULT_PTE ACCESS_TYPE_VIRT_READ` at the *identical* faulting GPU virtual address `0x286_80003000`. The host rebooted itself ~2.5 minutes after the second fault (confirmed via `uptime`, `who -b`, and a fresh NVRM driver reload at 13:08:27 plus a "journal corrupted or uncleanly shut down" message) -- this was a full, uncommanded power-cycle of the physical host, not an app-level crash.

Cross-checking node 2 (`spark-276f`, up continuously 4 days, never rebooted) put this in perspective: it has logged **44+ of the same `NV_ERR_NO_MEMORY` events and 3 separate Xid 31 faults at the exact same address** over its 4-day uptime, spread hours to days apart, without ever crashing the host. This means: (1) the fragmentation-driven allocation failure is a frequent, mostly-silent, *ambient* background condition on this whole fleet -- not something specific to explicit 240K-token tests, just far more likely to matter there; (2) a Xid 31 fault alone does not normally take a host down; (3) node 1's outcome today was the unusual case, most plausibly because two Xid faults landed only 9 minutes apart -- denser than anything in node 2's 4-day history -- itself a likely side effect of this session's own rapid crash/stop/reboot test cycling rather than a property of the recipe under normal operation. Checked node 1's thermal/power state directly (`nvidia-smi -q`): 41degC against a 55degC limit, no HW/SW thermal slowdown, no power braking active -- hardware/thermal is clean; ECC counters are not exposed at all on this integrated GB10 GPU (`N/A`, not zero), so that specific corroborating signal is unavailable. The identical fault address recurring across two physically distinct GPUs/nodes strongly suggests a fixed, deterministic GPU-virtual-address allocation (plausibly something in the CUDA-graph-capture or unified-memory page-fault handling path on this Grace-Blackwell coherent-memory architecture) rather than per-node hardware defects.

**Practical upshot**: the 240K memory-pressure risk and this new host-reboot escalation path are almost certainly the same underlying fragmentation mechanism at two different severities, not two separate bugs. Recommended mitigations for a future session, none yet implemented: (a) build a lightweight proactive-compaction or `nr_free_pages_blocks`-aware pre-flight check into `prelaunch_flush.sh` rather than relying on `MemAvailable`-percentage margins; (b) avoid tight retry loops after any boot failure on this fleet -- add a real cooldown between attempts so repeated Xid faults don't stack close together; (c) escalate to NVIDIA/driver-level reporting given the deterministic fault address is reproducible across two independent nodes; (d) keep the 240K settled-vs-fresh-boot distinction in mind for any future capacity planning.

**Status as of this writeup**: production is down. The first two restore attempts after the reboot both failed (NCCL error, then the illegal-memory-access/Xid-31 fault that preceded discovering node 1 had power-cycled); node 1 confirmed healthy post-reboot (clean thermal, no lingering processes) but a third boot attempt was deliberately not made pending explicit user sign-off, given the severity of what a repeat Xid 31 has already shown it can do to this host. Both nodes are currently clean and idle.

**Update**: user authorized the retry. Fourth boot attempt sailed through the CUDA graph capture point cleanly (no NCCL stall, no NVRM/Xid event on either node) and reached `Application startup complete`; a real chat completion round-tripped correctly. Production restored on `v15-combined`. Added a fragmentation-aware pre-flight check to `recipes/scripts/prelaunch_flush.sh` (new `recipes/scripts/frag_check_remote.sh`): reads `nr_free_pages_blocks` on each host right after the drop_caches flush, and if below a conservative threshold (2,000 -- comfortably between the observed-crash value of 0 and the two observed-healthy values of 49,152/147,456), attempts a synchronous kernel compaction pass (`/proc/sys/vm/compact_memory`) and reports whether it helped. Advisory (WARN, not a hard fail) since the threshold is based on two data points, not a validated statistical floor. Tested against both live production nodes with no disruption (drop_caches/compaction only touch host page cache, not the running process's memory).

## MiaAI-Lab update analysis: adaptive-k (skip) and FP8 dense projections (real candidate, provisional)

User asked for an analysis of MiaAI-Lab's latest upstream update (their repo posted PR #139, "adaptive-k + FP8 dense decode," merged 2026-09-08) -- investigate-only, no build changes, since production traffic was live at the time of the analysis itself. Fetched `/home/luser/build-exl3-v2` (`c190db1` -> `9c0794b`, 38 new commits since our last known baseline). Filtering out what this project already has (E3 kernel, tp4 experimental, doc updates) and the AGPL-3.0 relicense (not a technical decision -- already agreed to in the plan that opened this project's E3/vLLM-PR investigation), two substantive new features plus one operational fix remained.

**`GLM53_ADAPTIVE_K` (adaptive verification length) -- evaluated, not portable to this fleet.** Reads a per-request EMA of accepted draft tokens to trim per-step verification to a shorter prefix from a candidate set `{2,4,7}`, keeping the batch uniform so CUDA graphs still apply. Read the actual patch (`overlay/patch_adaptive_k.py`), not just the commit message: this mechanism is built entirely around **DFlash2's fixed 8-token (1 anchor + 7 draft) drafter block** -- the whole value proposition is "verify a shorter prefix of the 7 drafted tokens when acceptance has been running low." This fleet runs **MTP-2** (2 speculative tokens per step), with no 7-token block to trim a prefix of -- the mechanism has nothing to act on here. Upstream's own README lists "MTP k=2 baseline ~24.6 tok/s" as a comparison point, which lines up almost exactly with this fleet's own measured 24.7-28.0 tok/s decode baseline (`v15-combined` sanity checks throughout this document) -- confirming this fleet is the config the patch has nothing to offer, not a version-drift excuse to dismiss it on.

**`GLM53_DENSE_FP8` (FP8 weight-only dense projections) -- real, architecture-generic, explicitly provisional.** Quantizes the BF16 dense linear layers (shared-expert MLP, dense-MLP, KDA and MLA linear-attention projections, group-selectable) to FP8 e4m3 via the Marlin kernel, independent of speculative-decoding scheme -- unlike adaptive-k, this is directly applicable regardless of MTP vs. DFlash2. Upstream's own measured numbers: ~11ms less per decode step, +10% on counting, **+12-19% on prose alone** (the relevant comparison point, since we can't use their stacked "+37% with adaptive-k" number), measured on their own `sparkDash` prose bench. Read the actual diff (`overlay/exl3.py`'s `Glm53DenseFp8Method`/`_glm53_dense_fp8_group`, `overlay/patch_dense_fp8.py`'s `kda.py`/`model.py` constructor edits) rather than trusting the summary -- confirmed both patch anchor strings (`kda.py`'s `saved_quant_config` constructor lines, `model.py`'s `quant_config=None,  # MLA projections are BF16 in checkpoint` line) match this image's actual installed vLLM source byte-for-byte, and confirmed the `get_quant_method` dispatch graft point in our own `overlay/exl3.py` (already carrying E3's grouped-MoE tier) matches upstream's diff context exactly despite our file's other divergence -- a clean graft, not a guess.

**This is explicitly a lossy, unvalidated-even-by-its-authors change**, per upstream's own commit message: *"PROVISIONAL: changes target numerics; needs a KLD panel before it can become a default."* Their own proxy measure (KL vs. stock 0.002-0.013 nats/position, argmax agreement 94-100%) means up to ~6% of decode positions can have a different top-token choice than stock BF16 -- a real accuracy trade-off, not a free win, and upstream hasn't finished validating it themselves. One more corroborating data point, independent of this project's own fragmentation investigation above: upstream's notes say running FP8 dense *without* capping KV cache dropped their head node to **~1.5 GiB MemAvailable at 850K context** -- another team hitting the same host-memory-margin fragility class this project just spent a full session root-causing, on the same hardware class. Not a new risk from their patch itself, but a reason to be even more disciplined about memory margin if this project tests it.

**The launcher image-sync fix (`0fec07a`)** -- fixes a bug in upstream's own `start.sh`'s head/worker image-identity comparison (RepoDigests vs. RootFS.Layers mismatch causing needless full-image re-shipping on every restart). Not applicable: this project uses `sparkrun`'s own `docker save | ssh | docker load` distribution mechanism, a different code path entirely with no analogous comparison to fix.

**Verdict**: adaptive-k is not worth chasing further (no portable value on this config). Dense-FP8 is worth a properly-gated experiment, not an adoption -- given it's lossy and unvalidated even by its authors, it gets the same tinyGLM-gate-then-real-checkpoint-A/B treatment as every other change this project has promoted, but held to a *higher* bar than usual: the real-checkpoint validation must include an explicit output coherence/accuracy check (side-by-side same-seed completions, FP8 on vs. off), not just a throughput number, since this is the first candidate in this project's history where the tradeoff is genuinely "some accuracy risk for some speed" rather than a free or correctness-neutral change.

The prefill regression is new information -- upstream's own benchmarks are entirely decode-oriented (`sparkDash Decode bench`), so they never measured this tradeoff at all. Most likely mechanism: the boot log's own warning (`marlin_utils.py:238`, "Marlin requires thread-tile padding for some weight shapes in this model... performance may be degraded") -- the Marlin FP8 kernel is optimized for the memory-bandwidth-bound, single-token decode regime, and adds overhead relative to EXL3's already-well-optimized native kernel for prefill's large batched GEMMs.

**Coherence check** (2 same-seed, temperature-0 prompts, FP8 on vs. off): both a factual-explanation prompt (why the sky is blue) and a math-reasoning prompt (a two-trains meeting-time problem) produced **correct, coherent, on-topic answers in both configurations** -- the trains problem's arithmetic (100 mph combined, 3 hours, 180/120 miles) was exactly right both ways. Divergence was real but benign: different word choice and formatting past the first sentence or so (matching upstream's own "94-100% argmax agreement" framing -- some token positions do flip, but output quality held up in both samples tested). A 2-prompt sample is not a rigorous accuracy panel, but found zero evidence of the kind of qualitative degradation that would make this an easy reject on correctness alone.

**Verdict: validated, NOT promoted.** The real, controlled prefill regression (-12.4% @16K, -14.7% @64K) is the deciding factor: this fleet's actual production traffic is long-context-prefill-dominated (this project's own earlier finding: ~101.5K average prompt tokens), so a double-digit prefill cost is a real, direct hit to the workload this fleet actually serves, not a hypothetical one -- it outweighs the genuine +12% decode win for this deployment's specific traffic shape, even setting the accuracy-risk question aside entirely. This is a negative-but-honest result of the same kind this project has reached before (the `busy_loop_s`/`GLM53_SPINWAIT_MS` CPU-reduction claim, `gpu_memory_utilization=0.85`): the upstream feature works exactly as its authors describe, on exactly the numbers they measured, and is still the wrong choice for this fleet's own workload, not a bug. `v15-combined` remains production, unchanged. `glm53-exl3-v16-densefp8:local` and its two recipes are kept in the tree as a validated, documented, available-but-not-shipped option -- worth revisiting only if this fleet's traffic profile shifts toward shorter, decode-heavy requests, or if a future upstream fix narrows the Marlin padding overhead specifically.

**Not pursued further, deliberately, given diminishing returns after a clear result**: isolating which specific group (`dense` vs. `kda` alone) drives the prefill regression -- `kda`'s memory-bound linear-attention recurrence is a plausible candidate for having a smaller prefill cost than `dense`'s large batched GEMMs, but confirming that would need its own boot cycle and doesn't change today's verdict either way. Queued as a real, worthwhile refinement for a future session if this feature is ever revisited.
